# Склад і виробництво зовні: виклики, ключ, підводні камені

Нотатка для ролі інтерфейсу: що ядро дає зовнішньому складському клієнтові і що в
нативному Odoo 19 поводиться не так, як здається. Звідси матеріал переїжджає в
`docs/api/screens.md` - розділ «склад» пише роль інтерфейсу, ядро сюди кладе
факти. Відповідь на запити 2026-09-22-006, -007, -008, -010.

## Ключ API замість пароля адміністратора

Службовий користувач і ключ заводяться скриптом:

```
python3 scripts/api_key.py --db payroll             # стенд 8130
python3 scripts/api_key.py --db cw_проба --once     # разовий контейнер
```

Логін `sklad_api`, назва «склад», групи рівно три: `base.group_user`,
`stock.group_stock_user`, `mrp.group_mrp_user`. Жодної бухгалтерської - скрипт
сам падає, якщо користувач раптом опинився в `account.group_*` чи
`base.group_system`. Скрипт ідемпотентний щодо користувача: другий запуск не
створює двійника, а лише видає ще один ключ (старі лишаються чинними).

Три знання, на яких усе тримається:

1. **`res.users.apikeys._generate(scope, name, expiration_date)`** - підпис Odoo
   19, метод приватний. Публічний `generate()` спершу перевіряє ВЖЕ наявний ключ
   того самого користувача, тому перший ключ ним не зробити.
2. **Ключ дістається `env.user`, а не переданому користувачеві.** Виклик іде
   `env["res.users.apikeys"].with_user(user).sudo()._generate(...)`: `with_user`
   ставить власника, `sudo` дозволяє безстроковий ключ. Без `sudo` Odoo вимагає
   дату закінчення в межах `api_key_duration` групи.
3. **Безстроковий ключ мусить бути ГЛОБАЛЬНИМ: `scope=None`.** Перевірка bearer
   кличе `_check_credentials(scope='rpc')`, а такої області не існує - у коді
   Odoo прямо написано, що підходить лише ключ без області. Ключ зі `scope="rpc"`
   мовчки не пускає.

Виклик після цього звичайний:

```
POST http://<стенд>/json/2/stock.location/search_read
Authorization: Bearer <ключ>
X-Odoo-Database: payroll
{"domain": [["usage", "=", "internal"]],
 "fields": ["complete_name", "ua_capacity", "ua_capacity_used"], "limit": 3}
```

Базу вибирає заголовок `X-Odoo-Database` (перевірено на разовому контейнері).
Сеансова кука лишається потрібною тільки для PDF (`/report/pdf/...`) - bearer
там не працює.

Ключ показується один раз: Odoo зберігає лише хеш. Місце ключа - 1Password
(ToolKit > odoo-live), не файл поруч із кодом.

Дрібниця, яку варто знати: `all_group_ids` службового користувача покаже більше,
ніж три групи - «Technical Features», «Multi Currencies» і подібні приходять
неявними наслідками нативних груп. Своїх прав ми не додаємо.

## Інвентаризація: три дієслова і мітка

| Виклик | Що робить |
| --- | --- |
| `ua.stock.inventory.ua_get_or_create(client_ref, vals=None)` | документ за міткою клієнта: є - віддає наявний, немає - створює |
| `ua.stock.inventory.action_fill(category_ids=None, location_ids=None)` | залити аркуш залишками, за потреби звузивши категорією і полицями |
| `ua.stock.inventory.action_start_count()` | чернетка -> підрахунок, коли рядки принесли свої |
| `ua.stock.inventory.plan()` | що зробить проведення і що йому заважає |
| `ua.stock.inventory.action_apply()` | провести |

- **Мітка операції** - `ua_client_ref`, Char з індексом, не повторюється в межах
  компанії (`UNIQUE(company_id, ua_client_ref)`). Повторний виклик
  `ua_get_or_create` з тією самою міткою віддає ТОЙ САМИЙ документ і не чіпає
  його вміст. Захист від подвійного запису більше не треба тримати в памʼяті
  воркера.
- **`state` ззовні не пишеться.** Клієнт, що будує аркуш сам зі `stock.quant`,
  створює документ із `line_ids` і кличе `action_start_count()`.
- **Звуження.** `category_ids` бере категорії разом із дочірніми,
  `location_ids` - полиці разом із дочірніми і завжди в межах локації документа.
  Без аргументів поведінка стара: уся локація.
- **`plan()`** повертає список рядків `{text, level, target?}`, `level` -
  `info` / `warn` / `crit`, той самий вигляд, що в `ua.period.close.plan()`. Хоч
  один `crit` - `action_apply()` впаде, кнопка підтвердження нічого не змінить.
  Перешкоди рівно дві: стан не «Підрахунок» і дата в майбутньому. Решта рядків
  описує, що ляже: скільки розбіжностей, рядок на кожну (до 20), сума лишку з
  поясненням 947 -> 719, сума нестачі, дата проводок.

## Приймання і переміщення: та сама мітка на доставці

| Виклик | Що робить |
| --- | --- |
| `stock.picking.ua_get_or_create(client_ref, vals=None)` | доставка за міткою клієнта: є - віддає наявну, немає - створює |

- **Мітка операції** - `stock.picking.ua_client_ref`, Char з індексом, не
  повторюється в межах компанії (`UNIQUE(company_id, ua_client_ref)`). Порожня
  мітка дозволена скільки завгодно разів - поле потрібне лише тому, хто працює
  ззовні.
- **`origin` для цього більше не потрібен.** Мітка `WEB/<opId>` в `origin`
  нічого не гарантувала: `origin` це підстава документа, він не унікальний і в
  нього пишуть люди. Тепер `origin` вільний під справжню підставу (номер
  замовлення, накладна постачальника).
- **Повторний виклик віддає ТУ САМУ доставку і не чіпає її вміст**: клієнт після
  обриву звʼязку повторює запит, а не переписує вже прийнятий товар. Тримати
  захист від подвійного запису в памʼяті воркера не треба.
- **Компанію вирішує вид документа.** `stock.picking.company_id` - збережене
  `related` від `picking_type_id`, писати його марно. Тому виклик визначає
  компанію так: спершу компанія переданого `picking_type_id`, далі `company_id`
  зі значень, далі компанія викликача - і саме в ній шукає мітку.
- **Мітка без вигадок.** Порожній `client_ref` - помилка, документ не
  створюється.
- Поле видно у формі доставки на вкладці «Додаткова інформація».

## Карта складу: місткість і габарит

| Поле | Модель | Що це |
| --- | --- | --- |
| `ua_capacity` | `stock.location` | Integer «Місць». Руками. Нуль - не задано |
| `ua_capacity_used` | `stock.location` | Integer «Зайнято місць», обчислюване, НЕ зберігається |
| `ua_size` | `product.template` | Selection «Габарит»: `s` / `m` / `l` = 1 / 4 / 16 місць |

`ua_capacity_used` = сума «кількість × габарит» по залишках локації РАЗОМ З
ДОЧІРНІМИ, округлена вгору. Порожній габарит = 1 місце. Полиця переповнюється
від штук, а не від назв товарів, тому рахується кількість, а не кількість різних
позицій. Переповнення (зайнято > місць) нічого не блокує - це показник для карти.
Обмеження розкладання вміє нативна `stock.storage.category`, і вона лишається на
місці: наші два поля лише рахують заповнення.

Поле обчислюване і без `store`, тому в `docs/api/inventory.md` його немає - там
лише збережені поля. Читається звичайним `read` / `search_read`.

**Читати можна пачкою.** `search_read` на сотню полиць робить РІВНО ОДИН запит
до квантів на весь набір: підлеглі локації беруться однією вибіркою, кванти -
одним `_read_group` по (локація, товар), сума піднімається деревом через
`parent_path`. Тому карту складу не треба тягнути по локації за раз; числа від
цього не міняються, це та сама сума з тим самим округленням угору.

## Складальна карта виробу

`product.template.ua_assembly()` - лише читання, повертає:

```json
{"drawing_svg": "<svg …>|null",
 "drawing_name": "shershen-7.svg|null",
 "operations": [{"name": "Збирання рами", "workcenter": "Рама",
                 "time_minutes": 20.0,
                 "parts": [{"pos": 1, "product": "Рама карбон",
                            "qty": 1.0, "bin_location": "WH/Stock/Полиця М1"}],
                 "steps": ["Розпакувати раму"], "checks": ["Люфтів немає"]}]}
```

- **Креслення** - `product.template.ua_drawing_svg` (Binary, `attachment=True`)
  плюс `ua_drawing_name`. У карті приходить РОЗКОДОВАНИМ текстом SVG, не base64:
  екран вставляє його як є. Домовленість про вміст: елемент позиції має id
  `bom-N`.
- **Номер позиції `pos`** - порядок рядків специфікації (`sequence`, далі `id`),
  з одиниці. Окремого поля «номер позиції» немає свідомо: два джерела правди про
  порядок розійшлися б після першого ж перетягування рядка.
- **Кількість `qty`** - на ОДНУ одиницю виробу, в одиниці виміру компонента.
  Специфікація на партію 2 із 4 моторами дасть 2.
- **`bin_location`** - спершу правило розкладання
  (`location._get_putaway_strategy`), далі локація найбільшого залишку в складі
  компанії, далі `null`.
- **Групи операцій** ідуть у порядку маршруту (`sequence`). Рядки без операції -
  остання група «Без операції» з нульовим часом і порожніми кроками. Виріб без
  специфікації віддає `operations: []`.

### Що дає нативний CE 19, а що додали ми

- `mrp.bom.line.operation_id` («Споживається в операції») - **нативне поле
  самого `mrp`**, Enterprise `mrp_workorder` для нього не потрібен. У формі
  специфікації воно під групою `mrp.group_mrp_routings`.
- `mrp.routing.workcenter` нативно має назву, робочий центр, `sequence`, норму
  часу `time_cycle_manual` (хвилини) і рахунок `time_cycle` / `time_total`.
- Місця під текст у нього НЕМАЄ: ні опису, ні нотатки - аркуш операції
  (`worksheet`) і контрольні точки якості приходять з Enterprise. Тому додано два
  текстові поля: `ua_steps` «Кроки» і `ua_checks` «Перевірка», по пункту в рядок.

## Нативні дрібниці, що коштують години

- **У `stock.move` немає поля `name`** (`_rec_name = 'reference'`). `create` з
  `name` падає. Опис позиції - `description_picking`.
- **`stock.picking.button_validate()` без контексту повертає опис вікна
  майстра**, а не `True`. Щоб провести без дозамовлення:
  `with_context(skip_backorder=True, picking_ids_not_to_backorder=picking.ids)`.
  Обидва ключі читає нативний `stock_picking.py`.
- **`res.company` з `limit=1` віддає НЕ ту компанію.** Демо багатокомпанійне;
  брати треба компанію користувача (`env.user.company_id`) або за назвою.
- **Види документів шукаються через `picking_type_code`** (`incoming`,
  `outgoing`, `internal`) - і на `stock.picking`, і на `stock.move.line`
  (`picking_code`).
- **Рухи розкладаються на види** полями `stock.move.line`: `location_usage`,
  `location_dest_usage`, `production_id`, `is_inventory`.
