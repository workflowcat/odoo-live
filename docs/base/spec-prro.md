# l10n_ua_prro: фіскальні чеки ПРРО

Модуль `addons/l10n_ua_prro`. Залежності: `account`, `bp_bridge`. Тести: тег `ua_prro`.

Odoo не є ПРРО: ключ касира, підпис і зв'язок з податковою тримає сервіс ПРРО (Checkbox,
Вчасно.Каса або власний адаптер до фіскального сервера ДПС). Odoo складає чек з документів обліку,
шле його в міст інтеграцій і зберігає фіскальний номер. Адреса моста - лише із середовища
(`BP_BRIDGE_URL`, `BP_BRIDGE_TOKEN`), у модулі адрес немає.

## Шлях чека

1. Каса ПРРО (Облік - Налаштування - Каси ПРРО) прив'язана до журналів готівки і термінала. У
   журналі - форма оплати в чеку: готівка, картка, безготівково.
2. Покупець платить рахунок чи чек продажу через «Зареєструвати оплату» в такому журналі.
3. Сплачено рівно суму документів - чек по товарах: назва, код, штрихкод, кількість, ціна з ПДВ,
   знижка, сума, ставка й літера податку. Інакше (частина, кілька оплат) - один рядок на ставку ПДВ,
   сума ділиться пропорційно сумам документів.
4. Чек іде в міст. Відповідь з фіскальним номером - чек «фіскалізовано». Збій - чек «не надіслано»,
   оплата лишається; планувальник повторює кожні 15 хвилин, до 20 спроб, з тим самим ключем.
5. Повернення (оплата кредит-ноти в журналі каси) посилається на фіскальний номер чека продажу.

Навчальний режим каси нікуди не ходить: номер «ТЕСТ-…», Z-звіт «Z-ТЕСТ-…».

## Маршрути моста

Усі - `POST`, тіло і відповідь JSON. Помилка - статус від 400 і `{"error": "текст"}`.

`/api/prro/receipts` - фіскалізувати чек.

```json
{
  "id": "uuid чека: ключ ідемпотентності, той самий при повторі",
  "register": "фіскальний номер ПРРО", "provider": "checkbox",
  "kind": "sale | return | service_in | service_out",
  "number": "ФЧ/2026/00001", "total": 285.0,
  "payments": [{"type": "cash | card | cashless", "sum": 285.0}],
  "goods": [{"code": "BAT6S", "barcode": "4820000000017", "name": "...", "unit": "шт",
             "quantity": 2.0, "price": 120.0, "discount": 0.0, "sum": 240.0,
             "taxes": [{"rate": 20.0, "letter": "А"}]}],
  "related": "фіскальний номер чека продажу (для повернення)",
  "email": "покупець для електронного чека", "shift": "зміна в сервісі або null"
}
```

Відповідь: `{"fiscal_code": "...", "fiscal_date": "YYYY-MM-DD HH:MM:SS", "url": "посилання на чек",
"shift": "ід зміни в сервісі", "offline": false}`. Службові операції йдуть без `goods`.

`/api/prro/shifts/close` - Z-звіт.

```json
{"register": "...", "provider": "checkbox", "shift": "ід зміни або null",
 "totals": {"receipts": 3, "sales": 285.0, "returns": 0.0, "service_in": 500.0, "service_out": 200.0}}
```

Відповідь: `{"z_number": "...", "url": "...", "totals": {"sales": ..., "returns": ...}}`. Якщо суми
сервісу не збігаються з чеками в обліку, зміна позначається «розбіжність» і в історії лишається
порівняння.

## Чого ще немає

- Чеки з каси `point_of_sale`: паперовий чек POS друкується до відповіді сервісу, тому потрібен
  окремий модуль із JS - наступний крок.
- Проводки із Z-звіту: виручка вже в обліку через рахунки й оплати, Z-звіт лише звіряється.
- Літери податків задає бухгалтер у картці податку так, як їх налаштовано в сервісі ПРРО.
