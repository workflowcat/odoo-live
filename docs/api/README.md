# Як інтерфейс розмовляє з ядром

Ядро (`odoo-live`) тримає логіку українського бек-офісу. Інтерфейс - тема всередині
Odoo, екран на OWL або зовнішній клієнт - живе окремо і НЕ читає код ядра. Він читає
цю теку:

| Файл | Що це |
| --- | --- |
| `README.md` | ця сторінка: протокол, вхід, три дієслова, форми даних, правило версій |
| `inventory.md` | усі публічні методи і поля ядра з підписами; генерує `scripts/api_inventory.py` |
| `inventory.json` | те саме машинно, для перевірок і генерації клієнтів |
| `screens.md` | вісім робочих процесів: які саме виклики робить екран, із справжніми відповідями |
| `CHANGELOG.md` | що прибрано або перейменовано; додане сюди не пишеться |

Опис звіряється з кодом автоматично: `python3 scripts/contract_check.py` падає, якщо
`inventory.md` розійшовся з тим, що зараз у `addons/`, або якщо публічний метод зник
без рядка в `CHANGELOG.md`. Перевірка стоїть першою в `scripts/check_all.sh` і стенду
не потребує.

## Протокол

Odoo 19 CE дає три входи. Усі три ведуть до того самого коду; різниця в тому, хто
тримає сеанс.

### 1. Сеансовий: `POST /web/dataset/call_kw`

Те, чим користується власний веб-клієнт Odoo. Підходить темі й екрану на OWL - вони
вже всередині сеансу, кука `session_id` стоїть.

```
POST /web/dataset/call_kw
Content-Type: application/json

{"jsonrpc": "2.0", "method": "call", "params": {
  "model": "ua.api", "method": "month_summary",
  "args": [1, 2026, 9], "kwargs": {"context": {"lang": "uk_UA"}}}}
```

### 2. Зовнішній, класичний: `POST /jsonrpc`

Те, чим користуються наші скрипти (`scripts/*_check.py`). Двоходовий: спершу вхід,
далі виклики. Пароль (або ключ) іде в КОЖНОМУ виклику - сеанс не зберігається.

```
POST /jsonrpc
{"jsonrpc":"2.0","method":"call","params":{
  "service":"common","method":"login","args":["demo","<логін>","<пароль або ключ>"]}}
-> {"result": 2}

POST /jsonrpc
{"jsonrpc":"2.0","method":"call","params":{
  "service":"object","method":"execute_kw",
  "args":["demo", 2, "<пароль або ключ>", "ua.api", "month_summary", [1, 2026, 9], {}]}}
```

Порядок аргументів `execute_kw`: база, uid, пароль, модель, метод, список позиційних
аргументів, словник іменованих.

### 3. Зовнішній, сучасний: `POST /json/2/<модель>/<метод>`

З'явився в Odoo 19 (`addons/rpc/controllers/json2.py`). Без сеансу, без uid, без
пароля в тілі: лише заголовок `Authorization: Bearer <ключ>`. Аргументи іменовані,
і це найзручніший вхід для зовнішнього клієнта.

```
POST /json/2/ua.api/month_summary
Authorization: Bearer <ключ>
Content-Type: application/json

{"company_id": 1, "year": 2026, "month": 9}
```

Перевірено на демо: без ключа маршрут відповідає `401 Invalid apikey` із заголовком
`WWW-Authenticate: Bearer`.

Обмеження маршруту, про які варто знати наперед:
- метод має бути публічним (без підкреслення) і не позначеним `@api.private`;
- метод із `@api.model` кличеться без `ids`; метод запису - з `"ids": [...]`;
- `context` передається окремим ключем тіла: `{"ids": [7], "context": {"lang": "uk_UA"}}`.

## Вхід: сеанс або ключ

**Сеанс.** `POST /web/session/authenticate` з `{db, login, password}` ставить куку
`session_id`. Далі всі виклики `call_kw` ідуть із нею. Це шлях теми й екранів усередині
Odoo; зовнішньому клієнтові він незручний через CSRF-заголовки.

**Ключ API.** Odoo 19 CE має модель `res.users.apikeys` (у `base`, окремий модуль не
потрібен). Ключ створює САМ користувач: меню користувача > «Мій профіль» >
«Обліковий запис і безпека» (Account Security) > «Новий ключ API». Форма просить
пароль, назву і дату закінчення; значення показується ОДИН раз, у базі лежить лише
його хеш.

Що з цього випливає для UI:
- ключ підставляється замість пароля в `execute_kw` (Odoo сам звіряє його як ключ
  зі сферою `rpc`) або йде в заголовку `Bearer` для `/json/2`;
- ключ успадковує права свого користувача, своїх прав не має; окремої «службової
  ролі» він не створює - заводьте окремого користувача з потрібними групами;
- дата закінчення обов'язкова для всіх, крім адміністратора, і обмежена правами
  групи (`api_key_duration`); протермінований ключ Odoo прибирає сам;
- ключ - секрет: у репозиторії, у `.env` з реальним значенням і в логах його немає.

## Три дієслова екрана

Будь-який наш екран складається з трьох рухів, і більше жодного.

**1. Читати.** Стандартні `search_read` / `read` / `fields_get` для переліків і форм,
плюс наші складені читання, коли екрану треба те, що інакше збиралося б з десяти
викликів:

| Виклик | Що віддає |
| --- | --- |
| `ua.api.month_summary(company_id, year, month)` | місяць зарплати цілком: період, перешкоди, план, підсумки листків, документи з перевірками |
| `ua.api.documents_for_month(company_id, year, month)` | вісім видів документів місяця з перевірками, у сталому порядку |
| `ua.api.employee_card(employee_id)` | картка працівника: вкладки, документи, накази, відпустки, військовий облік |
| `ua.api.reporting_status(company_id, year, month)` | стан кожного звіту робочого місця за період |
| `ua.api.record_checks(model, res_id)` | перевірки одного запису будь-якої моделі з `ua.checks.mixin` |
| `ua.api.warehouse_map(company_id)` | карта складу: дерево локацій, місткість, зайняті місця, переповнення, вміст полиці, призначення і місце зони на плані |
| `ua.api.stock_glance(company_id, location_ids, category_ids, query, offset, limit)` | залишки з мінімумом, потребою на місяць, «на скільки виробів вистачить» і габаритом; пошук і сторінки |
| `ua.api.floor_packages(company_id)` | нерозкладене: приймання, підлоги полиць, свіжий випуск із виробництва; з партією і категорією |
| `ua.api.product_assembly(product_id)` | складальна карта виробу: креслення, операції, позиції, полиці |
| `ua.api.inventory_plan(inventory_id)` | план проведення інвентаризації і чи пройде воно взагалі |
| `ua.api.workorder_card(workorder_id)` | картка наряду для кіоску цеху: кроки, пункти перевірки з відповідями, комплектуючі операції |

Решта читань - звичайні `get_*` моделей із `inventory.md`
(`ua.payroll.param.get_all`, `ua.cpi.index.get_map`, `ua.kp.code.suggest`...).

Усе, що зветься `ua.api.*`, ЛИШЕ читає. Запису там немає навіть у вигляді «створимо
чернетку, якщо її немає». Це перевіряють тести з тегом `ua_api`.

**2. Показати план.** Перед кожною незворотною дією екран питає ядро, що станеться:

| Виклик | Що віддає |
| --- | --- |
| `ua.period.close.plan(company, year, month)` | рядки `{text, level, target}`, level: `info` / `warn` / `crit` |
| `ua.period.close.blocker_rows(company, year, month)` | перешкоди `{key, text, short, plan, target}`; порожньо = можна |
| `ua.hire.case.action_hire_plan()` | те саме для прийняття на роботу |
| `ua.stock.inventory.plan()` | те саме для інвентаризації; через `ua.api.inventory_plan()` іде разом із шапкою документа і `can_apply` |

План - це читання. Порожній список перешкод означає «дія пройде».

**3. Діяти.** Кнопки моделей: `action_*`, `ua_compose(...)`, `ensure_for(...)`,
`ensure_run(...)`, `action_refill()`, `action_confirm()`. Вони пишуть у базу, тому
екран кличе їх лише у відповідь на явну дію людини, і після них перечитує дані
першим дієсловом. Дія повертає або `True`, або опис вікна Odoo
(`ir.actions.act_window`), або `{"type": "ir.actions.client", "tag":
"display_notification", ...}`.

## Форми даних, спільні для всього продукту

### Рядок перевірки

Кожен документ місяця рахує свої перевірки методом `_checks()` (домішка
`ua.checks.mixin`). Прапорець «ок» ніде не зберігається - перевірки рахуються щоразу.
Рядок завжди такий:

```json
{"level": "error", "text": "Немає рядка табеля для працівника з активним трудовим договором",
 "fact": "1", "target": {"model": "hr.employee", "domain": [["id", "in", [23]]]}}
```

- `level`: `ok` | `warn` | `error`;
- `text`: короткий український рядок, готовий до показу;
- `fact`: число або слово-факт, рядком;
- `target`: куди клікнути, щоб побачити саме ці записи, або `false`.

Підсумок документа - найгірший рівень плюс лічильники: `{"level", "errors", "warns"}`.
`ua.api.documents_for_month()` віддає і рядки, і підсумок.

`_checks()` приватний, і ззовні його не покличеш. Публічний вхід - одне читання для
будь-якого запису:

```
call("ua.api", "record_checks", ["ua.timesheet.sheet", 12])
```

```json
{"model": "ua.timesheet.sheet", "res_id": 12, "name": "Табель 03/2026", "has_checks": true,
 "level": "error", "errors": 1, "warns": 0,
 "checks": [{"level": "error", "text": "…", "fact": "1", "target": {"model": "hr.employee", "domain": [["id", "in", [23]]]}}]}
```

Модель без домішки віддає `has_checks: false`, `level: "ok"` і порожні `checks`.
Права - права самого запису (`check_access("read")`, з правилами компанії); чужий
запис - `AccessError`, неіснуючий запис або модель - `UserError`.

### Ціль (`target`)

Три види, і більше жодного:

| Вид | Значення |
| --- | --- |
| `{"xmlid": "l10n_ua_navigation.action_xxx"}` | наявна дія Odoo, за потреби з `domain` і `context` |
| `{"model": "hr.payslip", "res_id": 59}` | один запис у формі |
| `{"model": "hr.payslip", "domain": [...], "name": "Вересень 2026"}` | перелік записів за доменом |

Відкривається одним викликом: `ua.screen.open_target(target)`. Він повертає готовий
опис дії Odoo. Рядок виписки (`account.bank.statement.line`) відкривається у поданні
звірки - цей виняток живе в ядрі, не в інтерфейсі.

```json
{"type": "ir.actions.act_window", "res_model": "hr.payslip", "res_id": 59,
 "view_mode": "form", "views": [[false, "form"]], "target": "current"}
```

### Смуга періоду

Однакова на всіх екранах:

```json
{"year": 2026, "month": 9, "label": "Вересень 2026", "closed": false,
 "periods": [{"year": 2026, "month": 4, "label": "Квітень 2026", "current": false, "closed": false}]}
```

Шість місяців назад від обраного включно, від найстарішого до найновішого.
`ua.api.month_summary()` додає до неї `hard`, `closed_by`, `closed_date`.

### Пояснення числа

```
ua.explain.explain(model, res_id, field=None, when="auto")
```

Одна точка входу «звідки взялося це число» для будь-якої моделі, яка вміє себе
пояснювати. `field` звужує слід до потрібного кроку і кроків, чиї результати він
читає. `when`: `auto` (заморожений слід, якщо є, інакше перерахунок), `now` (завжди
перерахунок), `frozen` (лише заморожений, інакше `{"state": "none"}`).

У відповіді: `state` (`committed` / `preview` / `none`), `frozen`, `subject`, `params`
(правила з датою і підставою) і `steps` - кожен крок із формулою, входами, значеннями
входів і результатом. Перерахунок наживо чесно позначений `frozen: false` і поясненням
чому - інтерфейс не має видавати його за «так було тоді».

### Типи у відповідях

Дати - рядки `YYYY-MM-DD`, дата з часом - `YYYY-MM-DD HH:MM:SS`. Зв'язок - пара
`[id, назва]`, як його віддає `read()`. Порожнеча - `false`, не `null`. Домени -
списки списків. Кортежів у відповідях `ua.api` немає.

## Помилки

- **`UserError`** - текст написаний для людини і призначений до показу як є:
  «Місяць закрити не можна: непроведених листків: 20.». Не перекладайте, не
  переписуйте, не ховайте за власним «щось пішло не так».
- **`AccessError`** - бракує прав. Показуйте як є і не ховайте екран за порожнім
  станом: `ua.api` навмисно не робить `sudo()`, тому порожня відповідь ніколи не
  означає «немає прав».
- **`ValidationError`** - дані не проходять обмеження моделі; теж людський текст.
- Інше (`AttributeError`, `KeyError`, 500) - помилка ядра. Її показувати людині не
  треба: це `request` до ролі core через `scripts/agent_note.py`.

У JSON-RPC усі вони приходять як `error.data.message` плюс `error.data.name` із
класом винятку. Розрізняйте за `name`, а не за текстом.

## Підводні камені

Місця, де нативний Odoo 19 поводиться не так, як здається. Кожне коштувало комусь
години; перелік ведеться саме тому, що з `fields_get()` цього не видно.

### Склад і рухи

- **У `stock.move` немає поля `name`** (`_rec_name = "reference"`). `create` з `name`
  падає. Опис позиції - `description_picking`.
- **Кількість приймання пишеться на `stock.move`**, поля `quantity` і `picked`, а не
  на `stock.move.line`.
- **`stock.picking.button_validate()` без контексту повертає ОПИС ВІКНА майстра**
  дозамовлення, а не `true`. Щоб провести без дозамовлення, потрібні обидва ключі:
  `{"skip_backorder": true, "picking_ids_not_to_backorder": [<id>]}`. Обидва читає
  нативний `stock_picking.py`.
- **Види документів шукаються через `picking_type_code`** (`incoming`, `outgoing`,
  `internal`) - і на `stock.picking`, і на `stock.move.line` (там поле `picking_code`).
- **Рухи розкладаються на види** полями `stock.move.line`: `location_usage`,
  `location_dest_usage`, `production_id`, `is_inventory`. Окремого поля «вид руху»
  немає.
- **Внутрішній вид документа може бути вимкнений**: склад з одноступеневим прийманням
  створюється без нього. Шукайте з `{"context": {"active_test": false}}` і вмикайте
  явно.
- **Локація `WH/Input` теж буває вимкнена** - вона зʼявляється лише при двокроковому
  прийманні (`stock.warehouse.reception_steps`).

### Товар і категорія

- **`product.template.categ_id` у Odoo 19 не обовʼязкове і не має замовчування.**
  Товар без категорії - звичайна річ, і `child_of` з порожнім id валиться всередині
  ORM на `TypeError`, а не на людській помилці. Тому в `ua.api` категорія приходить
  як `false`, а не як `[0, ""]`, і порожні id зі звужень викидаються.
- **Тип товару** - `is_storable` (булеве), а не `type = "product"`: у 19 `type`
  лишився лише для `consu` / `service` / `combo`.
- **Габарит і місткість** - наші два поля: `product.template.ua_size` (`s`/`m`/`l` =
  1/4/16 місць, порожнє рахується як `s`) і `stock.location.ua_capacity` («Місць»,
  руками; 0 - не задано). `stock.location.ua_capacity_used` обчислюване і НЕ
  зберігається, тому його немає в `inventory.md` - читається звичайним `read` /
  `search_read`. Заповнення рахується по локації разом із дочірніми. Переповнення
  нічого не блокує: обмеження розкладання вміє нативна `stock.storage.category`, і
  вона лишається на місці.
- **Коди габариту - малими літерами**: `s`, `m`, `l`. Таблиця з ключами `S`/`M`/`L`
  не знайде жодного і мовчки впаде на замовчування - саме так «вільно 22» на картці
  полиці розійшлося з «влізе 5 з 8» у плані. Місць на штуку ядро віддає готовими:
  `sizes` у `warehouse_map`, `per_unit` у `floor_packages`.

### Компанії

- **`res.company` з `limit=1` віддає НЕ ту компанію**, коли баз кілька: демо
  багатокомпанійне. Брати треба компанію користувача (`env.user.company_id`) або за
  назвою. Усі читання `ua.api` приймають `company_id` першим аргументом саме тому.

### Виробництво

- **`mrp.bom.line.operation_id` («Споживається в операції») - нативне поле самого
  `mrp`**, Enterprise `mrp_workorder` для нього не потрібен. У формі специфікації воно
  під групою `mrp.group_mrp_routings`.
- **Місця під текст в операції маршруту нативно НЕМАЄ**: ні опису, ні нотатки - аркуш
  операції (`worksheet`) і контрольні точки якості приходять з Enterprise. Тому наші
  `mrp.routing.workcenter.ua_steps` і `ua_checks`, по пункту в рядок.
- **Норма часу операції** - `time_cycle_manual` (хвилини), рахунок - `time_cycle` /
  `time_total`.

### Ключ API

- **`res.users.apikeys._generate(scope, name, expiration_date)` приватний.** Публічний
  `generate()` спершу перевіряє ВЖЕ наявний ключ того самого користувача, тому першого
  ключа ним не зробити.
- **Ключ дістається `env.user`, а не переданому користувачеві**: виклик іде
  `env["res.users.apikeys"].with_user(user).sudo()._generate(...)`.
- **Безстроковий ключ мусить бути ГЛОБАЛЬНИМ, `scope=None`.** Перевірка bearer кличе
  `_check_credentials(scope="rpc")`, а такої області не існує: ключ зі `scope="rpc"`
  мовчки не пускає.
- **Базу вибирає заголовок `X-Odoo-Database`.** Сеансова кука лишається потрібною
  лише для PDF (`/report/pdf/...`) - bearer там не працює.
- Службовий користувач складу і його ключ заводяться скриптом
  `python3 scripts/api_key.py --db payroll`. Ключ показується ОДИН раз: у базі лежить
  лише хеш, місце ключа - 1Password, не файл поруч із кодом.

## Правило версій

`inventory.md` описує те, що є. `CHANGELOG.md` описує те, чого більше немає.

- **Додали** публічний метод або збережене поле - нічого писати не треба. Жоден
  інтерфейс від додавання не ламається; `contract_check.py` лише вимагає
  перегенерувати опис.
- **Прибрали або перейменували** - рядок у `CHANGELOG.md` у ТОМУ Ж коміті, з трьома
  речами: що зникло, що натомість, що робити інтерфейсу. Без цього
  `contract_check.py` падає.
- Перейменування ядро бачить як зникнення старої назви і появу нової, тому окремого
  правила для нього немає.
- Інтерфейс ніколи не пише в `addons/`. Бракує методу - `python3 scripts/agent_note.py
  new request --from ui --to core "…"`. Поки core не зробив, UI збирає потрібне з
  кількох викликів у себе.
- Опис синхронізується в репозиторій інтерфейсу скриптом `odoo-ui/scripts/sync_contract.sh`,
  який копіює цю теку і записує коміт ядра, з яким синхронізовано.
