# Зарплата для України на odoo-live

Гілка `payroll`, робоче дерево `/Users/kit/Codius/odoo-live-payroll`, локальний стенд на порту 8110, база `payroll`.
Платформа (міст, Supabase, KYC) лишається на `main`. Сюди зливаємо, коли десять еталонних сценаріїв сходяться до копійки.

## Що будуємо

Рушій: OCA `payroll` для Odoo 19 (правила як дані, розрахункові листки, пакети, категорії). Він уже працює з `hr.version`,
тобто з контрактами Odoo 19. Українська частина - наші модулі поверх нього:

| Модуль | За що відповідає |
|---|---|
| `l10n_ua_payroll_rules` | таблиця параметрів із датами (МЗП, ПМ, ПСП, ставки, максимальна база ЄСВ, святкові), структура «Україна: оклад», правила ПДФО, ВЗ, ЄСВ, ПСП, поля працівника (РНОКПП, категорія ЄСВ, основне місце або сумісник) |
| `l10n_ua_hr` | штатний розпис, накази і друковані форми П-1, П-3, П-4, повідомлення про прийняття, ЦПХ і ФОП як окремі види |
| `l10n_ua_time` | табель П-5, графіки, нічні, надурочні, вихідні, простій |
| `l10n_ua_average` | середня за Постановою 100 і за Постановою 1266, страховий стаж, частина ПФУ, резерв відпусток 471 |
| `l10n_ua_payroll_account` | проводки за підрозділами, платіжні відомості, файли зарплатних проєктів банків |
| `l10n_ua_payroll_reports` | об'єднана звітність з Д1, 4ДФ, Д5, Заява-розрахунок, 1-ПВ, розрахункові листки, перевірка XML за схемою ДПС |
| маршрути моста | подання через ЕДО, індекс Держстату, оновлення параметрів |

## Стан на 8 вересня 2026

Працює: рушій OCA payroll на Odoo 19, модулі `l10n_ua_payroll_rules` і `l10n_ua_average`, структура «Україна: оклад».
Усі десять сценаріїв рахуються (`python3 scripts/payroll_check.py`). Сценарії 6, 7, 8 (відпустка, лікарняний, компенсація)
рахує Odoo за Постановами 100 і 1266; їх числа ще має підтвердити бухгалтер.

Модуль середніх: історія заробітку за 12 місяців (вхідні залишки вручну, далі з проведених листків), типи відпусток
«Щорічна відпустка», «Тимчасова непрацездатність», «Без збереження зарплати», страховий стаж і відсоток лікарняних на працівнику,
правила VAC, SICK_EMP (дні 1-5), SICK_PFU (з 6-го дня), COMP_VAC (вхід «невикористані дні»).
Спрощення, які бухгалтер має підтвердити: одне вікно 12 місяців для обох постанов, виключені дні лише через поле «виключені дні»,
максимальна база ЄСВ у середній не обмежена помісячно.

Проводки (`l10n_ua_payroll_account`): карта «правило → Дт/Кт», рахунок витрат підрозділу (типово 92), журнал «ЗП», проводка
створюється при підтвердженні листка; перевірка звіряє обороти за рахунками 92, 661, 6411, 6415, 651, 378 на сценаріях 1 і 7.
План рахунків України завантажено на компанію стенда (`ua_psbo`).

Звітність (`l10n_ua_payroll_reports`): майстер «Об'єднана звітність (XML)» у меню Співробітники формує за місяць
Податковий розрахунок J0500111 з Д1 (J0510111) і 4ДФ (J0510411) у форматі ДПС (наказ 729, версія 11 з 17 липня 2026),
з іменами файлів за правилами ДПС і перевіркою за офіційними XSD (`schemas/`, з архіву реєстру форм ДПС). Шлях подання:
Odoo → XML → FreeZvit (перевірка) → Електронний кабінет або Сота (підпис, подання). Тест серпня 2026 валідний за всіма
трьома схемами; файли в Drive «Odoo зарплата / XML для FreeZvit».

Пакет для бухгалтера (8 вересня 2026): Google Drive → «Odoo зарплата»: таблиця «Еталонні сценарії зарплати 2026-09-08.xlsx»
(сценарії, рядки, проводки, параметри, припущення з жовтими клітинками для відповідей) і папка «Розрахункові листки» з PDF
кожного листка. Виправлення бухгалтера переносимо в `golden-scenarios.md` і в `scripts/payroll_check.py`.

## Правила стабільності

- Лише стандартний інтерфейс Odoo: списки, форми, канбан, статусбар. Без власних тем, CSS, JS і OWL-екранів.
- Модулі OCA лежать у `addons/` без змін. Оновлення OCA - заміна теки, не правки всередині.
- Українська логіка живе лише в наших модулях `l10n_ua_*`. Ядро Odoo і OCA не патчимо.
- Правила зарплати - дані (`hr.salary.rule`), параметри - таблиця з датами. У коді немає ставок і сум.
- Кожна зміна проходить `scripts/payroll_check.py`. Сценарій, що зійшовся з бухгалтером, не змінює очікувані числа.
- Версія модуля `19.0.x.y.z`; міграція на наступну версію Odoo - окрема гілка з тим самим набором сценаріїв.

## Як працювати

```bash
cd /Users/kit/Codius/odoo-live-payroll
```

## Інтеграції: що з'ясовано 8 вересня 2026

**Податкова (ДПС).** Прямий API існує: REST «Електронний кабінет», `https://cabinet.tax.gov.ua/cabinet/public/api/exchange/`,
методи `POST /report` (один звіт), `/reportzip` (пакет), `/kvt_by_id` (квитанції); тестовий контур на порту 9443.
Тіло - JSON із base64 підписаного і зашифрованого XML у транспортному контейнері (наказ 499), сам звіт - XML за форматом
наказу 729 і схемами XSD. Висновок: XML потрібен у будь-якому разі; питання лише, хто підписує і шифрує.
Три шляхи: (А) Odoo формує XML, людина вивантажує в кабінет і підписує в браузері - без коду підпису, крок ручний;
(Б) міст підписує і шифрує сам (бібліотека КЕП на сервері, ключ або хмарний КЕП) і шле в API - повна автоматизація,
відкрите питання: де живе ключ і хто відповідає за підпис; (В) провайдер (Вчасно, M.E.Doc) підписує і подає - платно,
залежність від провайдера. Порядок: спершу XML зі схемою (потрібен для всіх трьох), потім (А), потім (Б) після рішення про ключ.
Документація: https://cabinet.tax.gov.ua/help/api.html

**Банки.** ПриватБанк «Автоклієнт» API v3: `https://acp.privatbank.ua`, заголовок `token` з Приват24 для бізнесу, JSON;
виписки `GET /api/statements/transactions`, залишки `GET /api/statements/balance`, платежі `POST /api/proxy/payment/create`.
Monobank: корпоративний API для виписок, потрібна реєстрація застосунку (`https://api.monobank.ua/docs/corporate.html`).
Висновок: імпорт виписок і експорт платежів робимо через API в мості, файли лишаємо як запасний шлях.

**FreeZvit.** Безкоштовна програма для створення і перевірки звітів у XML ДПС; підпис і подання вона не робить.
Не залежність, а зразок. Що беремо з неї: реєстр форм з версіями і датами дії; вбудовані перевірки співвідношень
рядків; довідники як дані (ознаки доходів, категорії ЗО, ДПІ, КАТОТТГ); журнал звітів зі статусами і квитанціями;
друк заповненої офіційної форми. Усе це живе в Odoo, без зовнішніх програм і сховищ.

**OpenDataBot.** Уже підключений через міст; для зарплати не потрібен.

## Що ще треба зробити (беклог на 8 вересня 2026)

Зарплата, ядро:
- Д5 (трудові відносини): прийняття, звільнення, переведення, відпустки за місяць; повідомлення про прийняття (J3001001) до першого дня.
- Табель П-5 і графіки: нічні, надурочні, вихідні, простій, підсумований облік.
- Накази з друкованими формами П-1, П-3, П-4; штатний розпис.
- Індексація (індекс Держстату), матеріальна допомога з неоподатковуваною частиною, ЦПХ і ФОП-підрядники як окремі види.
- Аванс і остаточний розрахунок як два платежі; платіжні відомості; резерв відпусток на 471 (є в прототипі, перенести).
- Розрахункові листки українською (звіт QWeb замість англійського OCA).
- Заява-розрахунок до ПФУ за лікарняними.

Звітність і подання:
- Головна форма: перевірки співвідношень рядків (як у FreeZvit), не лише XSD.
- Журнал звітів: файл, статус, квитанція №1 і №2, дата подання; імпорт квитанцій.
- Прямий API ДПС: сервіс підпису і шифрування (нижче).

Платформа:
- Контейнер Odoo на Cloudflare після оплати плану; стенд для команди за посиланням.
- Банк: виписки і платежі через API ПриватБанк і Monobank у мості.
- Злиття гілки `payroll` у `main` після підтвердження сценаріїв бухгалтером.

## Прямий API ДПС: що з'ясовано і як робимо

Факти:
- REST API «Електронний кабінет»: `POST https://cabinet.tax.gov.ua/cabinet/public/api/exchange/report`, тіло
  `{"contentBase64": "...", "fname": "<ім'я файлу за наказом 729>"}`. Відповідь `ReturnReport`: `id`, `status`
  (`OK`, `ERROR_DECRYPT`, `ERROR_STRUCT_REPORT`, `ERROR_LINKED_DOCS`, `ERROR_SERTIF`, `ERROR_XSD`, `NOT_KVT`…),
  `kvt1Base64`/`kvt1Fname` (квитанція №1), `kvtList`. Квитанція №2 - `POST …/kvt_by_id` з `encryptedId`,
  у відповіді `kvtList[].finalKvt`. Тестовий контур `https://cabinet.tax.gov.ua:9443`.
- Реєстрації розробника немає. Договір про визнання електронних документів укладається автоматично при першому
  поданні з КЕП.
- Файл = XML за наказом 729, підписаний КЕП платника (внутрішній підпис, ДСТУ 4145), потім зашифрований на
  сертифікат ДПС (транспортний контейнер за наказом 499), потім base64.
- Криптографія: безкоштовна бібліотека ІІТ EUSignCP для Linux (iit.com.ua/downloads), кореневі сертифікати
  КНЕДП, сертифікати ДПС для шифрування (сторінка «Єдина адреса» на tax.gov.ua; змінюються, востаннє 6 серпня 2025).
- Так уже роблять інші: Prozorro (бот `fiscal_bot`: окремий сервіс підпису + цей API + опитування квитанцій) і
  Odoo-локалізація `NadozirnySvyatoslav/l10n_ua` (модуль `l10n_ua_tax_cabinet`: EUSignCP через ctypes, підпис,
  шифрування, подання, синхронізація документів з кабінету; ліцензії в репозиторії немає, код не копіюємо).

Дизайн для нас (три кроки):
1. Сервіс підпису `ua-sign` як контейнер поруч з Odoo: Debian + EUSignCP + Python; методи `sign`, `encrypt`,
   `sign_encrypt`, `decrypt` (для квитанцій); ключ КЕП і пароль - лише в його секретах; журнал усіх операцій.
2. Модуль `l10n_ua_dps_submit` в Odoo: кнопка «Подати в ДПС» на звіті → сервіс підпису → API → зберегти
   квитанцію №1, потім кроном забирати квитанцію №2; статуси на звіті; спершу тестовий контур 9443.
3. Рішення власника: чий КЕП (керівник чи бухгалтер) і де живе файл ключа. Без цього кроки 1-2 працюють лише
   на тестовому ключі.

## Правила Odoo 19, які вже коштували часу

- Групи оголошують через `res.groups.privilege` і `privilege_id`, не `category_id`.
- У пошуковому вигляді `<group>` без `expand` і `string`.
- Фільтр пошуку працює лише на збережених полях.
- Канбан-картка - `<t t-name="card">`.
- Контракт працівника - це `hr.version`; модуля `hr_contract` немає.
