# Зарплата для України на odoo-live

Гілка `payroll`, робоче дерево `/Users/kit/Codius/odoo-live-payroll`, локальний стенд на порту 8110, база `payroll`.
Платформа (міст, Supabase, KYC) лишається на `main`. Сюди зливаємо, коли десять еталонних сценаріїв сходяться до копійки.

## Що будуємо

Рушій: OCA `payroll` для Odoo 19 (правила як дані, розрахункові листки, пакети, категорії). Він уже працює з `hr.version`,
тобто з контрактами Odoo 19. Українська частина - наші модулі поверх нього:

| Модуль | За що відповідає |

| маршрути моста | подання через ЕДО, індекс Держстату, оновлення параметрів |

## Стенд у Cloudflare (з 9 вересня 2026)

- Worker `odoo-payroll` (https://odoo-payroll.botpartners.workers.dev) тримає Odoo у Cloudflare Container: `worker/wrangler.payroll.jsonc`, `worker/src/payroll.js`, образ з `odoo/Dockerfile` (wrangler збирає amd64 і вантажить у реєстр Cloudflare, 2-5 хвилин). Instance standard-1 (1/2 vCPU, 4 GiB), один екземпляр, сон через 45 хвилин без запитів, будильник cron `*/5 5-17 * * 1-5` UTC (пн-пт 08:00-20:00 Київ). Холодний старт близько 15 секунд.
- База `payroll` на Supabase (проєкт `odoo-live`, Франкфурт), користувач `odoo`. Вкладення в базі (`ir_attachment.location = db`). Перенесення: `pg_dump -Fc` локально → `pg_restore --no-owner --no-privileges --no-comments` через session pooler.
- Секрети Worker: PGHOST, PGPORT, PGUSER, PGPASSWORD, ODOO_ADMIN_PASSWD, BRIDGE_TOKEN (`wrangler secret bulk`). Entrypoint переписує `db_name`/`dbfilter` з `DB_NAME`.
- Викладка змін: `cd worker && npx wrangler deploy -c wrangler.payroll.jsonc`. Оновлення модулів після викладки: перезапуск контейнера з `INIT`-логікою не робить `-u`; поки що оновлення модулів роблять на локальному стенді, далі дамп → відновлення. Завдання: додати `UPDATE_MODULES` в entrypoint.
- Посилання для Лани https://odoo-demo.botpartners.workers.dev тепер веде на Worker; стан «прокидається» поки контейнер стартує. Тунель з Mac (`com.kit.odoo-payroll-tunnel`) вимкнено.
- Скрипти проти хмарного стенду мають слати браузерний User-Agent: Cloudflare відповідає 403 (1010) на Python-urllib.

- Оновлення модулів у хмарі: змінні Worker `MODULE_OPS` («i:mod1,mod2;u:mod3») і `MODULE_OPS_TAG` (будь-який новий рядок). Entrypoint виконує операції один раз на базу, запам'ятовує тег у `ir_config_parameter` (`bp.module_ops_tag`). Порядок: змінити vars у `wrangler.payroll.jsonc` → `wrangler deploy` → перший запуск контейнера робить `-i`/`-u` перед стартом Odoo (1-2 хвилини).
- Контрагенти з ЄДР: модуль `l10n_ua_partner_edr` (залежить від `bp_kyc` через міст `bp.bridge`): кнопка «Заповнити з ЄДР» у картці партнера, дія у списку, майстер «Контрагент з ЄДР» у меню Контакти, вкладка «ЄДР» (стан, КВЕД, керівник, капітал, ПДВ, маркери ризику), керівник як контакт, cron оновлення вимкнений. Дані з OpenDataBot через Worker `odoo-live` (`/api/odb/screen/:code`, кеш 24 год у D1).

- Інтерфейс для бухгалтера: модуль `l10n_ua_payroll_ui` збирає все в одне меню «Зарплата» (Розрахунок / Звітність / Кадрові документи / Довідники), перейменовує довідники і меню OCA українською (post_init_hook + міграції на кожну версію), ховає технічні коди у листку (колонка «Код» вимкнена, вмикається у списку), ховає для бухгалтера Обговорення, Календар, Дашборди, Тест, Додатки (лише base.group_system). Правила перейменовано коротко: «Оклад», «ПДФО 18 %», «ЄСВ 22 % за рахунок підприємства»…
- Бухоблік: OCA `account_usability` (меню «Бухоблік», проводки, банк і каса) і `account_financial_report` з `date_range`, `report_xlsx` (ОСВ = Trial Balance, Головна книга = General Ledger, журнали, відкриті позиції, PDF/XLSX). Без українського перекладу: наступний крок uk.po для цих модулів.
- Контейнер: standard-2 (1 vCPU, 6 GiB), регіон WEUR. Виміри до змін: авторизація 2,3 с, список 0,3-1,3 с, форма 0,6 с; локально 0,02 с. Причина: запити до бази у Франкфурт і пів процесора.

- Виправлення за специфікацією 2.0, черга R0 (11 вересня 2026; перелік розривів у `docs/payroll/gap-2.0.md`):
  - **Округлення.** Гроші округлюються за ROUND_HALF_UP через Decimal. Функція `tools.r2` доступна у формулах правил, `ua_round` - у коді. Вбудований `round()` Python округлює до парного, що для грошей неправильно. Жодне еталонне число не змінилося, але поведінка стала визначеною.
  - **Середня за відрядження.** Два повні місяці і фактично відпрацьовані робочі дні замість 12 місяців і календарних днів × 5/7. Історія заробітку дістала поле «Відпрацьовано робочих днів»; без нього середньої немає і береться денний оклад. Сценарій 29.
  - **Індексація.** Поріг 103 % наростаючим підсумком (параметр `index_threshold`), індекс місяця листка не застосовується до його оприлюднення (поле «Оприлюднено»), сума ділиться пропорційно ставці і відпрацьованому часу, після виплати починається новий цикл (поле працівника «Місяць останньої виплаченої індексації»). Сценарії 17, 27, 28.
  - **ЄСВ за декретом.** Допомога розподіляється за місяцями, мінімальний внесок перевіряється за кожен місяць окремо. Сценарій 30; сценарій 15 не змінився.
- Виплати поза зарплатою і нові утримання (`l10n_ua_payroll_rules`, категорія `NOESV` «Оподатковувані виплати без ЄСВ»): матеріальна допомога (пп. 170.7.3 ПКУ, межа на рік рахується з уже виплаченого цього року), подарунки (пп. 165.1.39, 25 % МЗП на місяць), вихідна допомога (ст. 44 КЗпП), компенсація за використання власного майна; утримання — профспілковий внесок, виконавчий документ (сума або %), відшкодування шкоди. База ПДФО і ВЗ = `GROSS + NOESV`, база ЄСВ лишається `GROSS + MAT`. ## Правила стабільності

- Лише стандартний інтерфейс Odoo: списки, форми, канбан, статусбар. Без власних тем, CSS, JS і OWL-екранів.
- Модулі OCA лежать у `addons/` без змін. Оновлення OCA - заміна теки, не правки всередині.
- Українська логіка живе лише в наших модулях `l10n_ua_*`. Ядро Odoo і OCA не патчимо.
- Правила зарплати - дані (`hr.salary.rule`), параметри - таблиця з датами. У коді немає ставок і сум.
- Кожна зміна проходить `scripts/payroll_check.py`. Сценарій, що зійшовся з бухгалтером, не змінює очікувані числа.
- Версія модуля `19.0.x.y.z`; міграція на наступну версію Odoo - окрема гілка з тим самим набором сценаріїв.

## Інтеграції: що з'ясовано 8 вересня 2026

**Податкова (ДПС).** Прямий API існує: REST «Електронний кабінет», `https://cabinet.tax.gov.ua/cabinet/public/api/exchange/`,
методи `POST /report` (один звіт), `/reportzip` (пакет), `/kvt_by_id` (квитанції); тестовий контур на порту 9443.
Тіло - JSON із base64 підписаного і зашифрованого XML у транспортному контейнері (наказ 499), сам звіт - XML за форматом
наказу 729 і схемами XSD. Висновок: XML потрібен у будь-якому разі; питання лише, хто підписує і шифрує.
Три шляхи: (А) Odoo формує XML, людина вивантажує в кабінет і підписує в браузері - без коду підпису, крок ручний;
(Б) міст підписує і шифрує сам (бібліотека КЕП на сервері, ключ або хмарний КЕП) і шле в API - повна автоматизація,
відкрите питання: де живе ключ і хто відповідає за підпис; (В) провайдер (Вчасно, M.E.Doc) підписує і подає - платно,
залежність від провайдера. Порядок: спершу XML зі схемою (потрібен для всіх трьох), потім (А), потім (Б) після рішення про ключ.
Документація: https://cabinet.tax.gov.ua/help/api.html

**Банки.** ПриватБанк «Автоклієнт» API v3: `https://acp.privatbank.ua`, заголовок `token` з Приват24 для бізнесу, JSON;
виписки `GET /api/statements/transactions`, залишки `GET /api/statements/balance`, платежі `POST /api/proxy/payment/create`.
Monobank: корпоративний API для виписок, потрібна реєстрація застосунку (`https://api.monobank.ua/docs/corporate.html`).
Висновок: імпорт виписок і експорт платежів робимо через API в мості, файли лишаємо як запасний шлях.

**FreeZvit.** Безкоштовна програма для створення і перевірки звітів у XML ДПС; підпис і подання вона не робить.
Не залежність, а зразок. Що беремо з неї: реєстр форм з версіями і датами дії; вбудовані перевірки співвідношень
рядків; довідники як дані (ознаки доходів, категорії ЗО, ДПІ, КАТОТТГ); журнал звітів зі статусами і квитанціями;
друк заповненої офіційної форми. Усе це живе в Odoo, без зовнішніх програм і сховищ.

**OpenDataBot.** Уже підключений через міст; для зарплати не потрібен.

## Що ще треба зробити (беклог на 8 вересня 2026)

Зарплата, ядро:
- Д5 (трудові відносини): прийняття, звільнення, переведення, відпустки за місяць; повідомлення про прийняття (J3001001) до допуску до роботи, можна в день прийняття.
- Табель П-5 і графіки: нічні, надурочні, вихідні, простій, підсумований облік.
- Накази з друкованими формами П-1, П-3, П-4; штатний розпис.
- Індексація (індекс Держстату), матеріальна допомога з неоподатковуваною частиною, ЦПХ і ФОП-підрядники як окремі види.
- Аванс і остаточний розрахунок як два платежі (типово 20-го аванс, 6-го залишок; не рідше двох разів на місяць, не більше 16 днів між виплатами; якщо дата випадає на вихідний, платимо раніше); платіжні відомості; резерв відпусток на 471 (є в прототипі, перенести).
- Розрахункові листки українською (звіт QWeb замість англійського OCA).
- Заява-розрахунок до ПФУ за лікарняними.

Звітність і подання:
- Головна форма: перевірки співвідношень рядків (як у FreeZvit), не лише XSD.
- Журнал звітів: файл, статус, квитанція №1 і №2, дата подання; імпорт квитанцій.
- Прямий API ДПС: сервіс підпису і шифрування (нижче).

Платформа:
- Контейнер Odoo на Cloudflare після оплати плану; стенд для команди за посиланням.
- Банк: виписки і платежі через API ПриватБанк і Monobank у мості.
- Злиття гілки `payroll` у `main` після підтвердження сценаріїв бухгалтером.

## Прямий API ДПС: що з'ясовано і як робимо

Факти:
- REST API «Електронний кабінет»: `POST https://cabinet.tax.gov.ua/cabinet/public/api/exchange/report`, тіло
  `{"contentBase64": "...", "fname": "<ім'я файлу за наказом 729>"}`. Відповідь `ReturnReport`: `id`, `status`
  (`OK`, `ERROR_DECRYPT`, `ERROR_STRUCT_REPORT`, `ERROR_LINKED_DOCS`, `ERROR_SERTIF`, `ERROR_XSD`, `NOT_KVT`…),
  `kvt1Base64`/`kvt1Fname` (квитанція №1), `kvtList`. Квитанція №2 - `POST …/kvt_by_id` з `encryptedId`,
  у відповіді `kvtList[].finalKvt`. Тестовий контур `https://cabinet.tax.gov.ua:9443`.
- Реєстрації розробника немає. Договір про визнання електронних документів укладається автоматично при першому
  поданні з КЕП.
- Файл = XML за наказом 729, підписаний КЕП платника (внутрішній підпис, ДСТУ 4145), потім зашифрований на
  сертифікат ДПС (транспортний контейнер за наказом 499), потім base64.
- Криптографія: безкоштовна бібліотека ІІТ EUSignCP для Linux (iit.com.ua/downloads), кореневі сертифікати
  КНЕДП, сертифікати ДПС для шифрування (сторінка «Єдина адреса» на tax.gov.ua; змінюються, востаннє 6 серпня 2025).
- Так уже роблять інші: Prozorro (бот `fiscal_bot`: окремий сервіс підпису + цей API + опитування квитанцій) і
  Odoo-локалізація `NadozirnySvyatoslav/l10n_ua`: 68 модулів для Odoo 19 під LGPL-3 (оновлено 4 вересня 2026,
  демо demo.ndev.online, вхід demo/demo). Серед них `l10n_ua_sign` і `l10n_ua_tax_cabinet` (EUSignCP через ctypes: підпис,
  шифрування, подання, синхронізація документів з кабінету), `l10n_ua_bank_privat`, `l10n_ua_bank_mono`,
  `l10n_ua_bank_openbanking`, `l10n_ua_hr_salary` з проводками і резервом відпусток, `l10n_ua_tax_4df`, ПРРО Checkbox.
  LGPL дозволяє взяти ці модулі до себе зі збереженням авторства.
  Оцінка 8 вересня 2026 на чистій базі стенда: `l10n_ua_sign`, `l10n_ua_tax_cabinet`, `l10n_ua_bank_privat`, `l10n_ua_bank_mono`,
  `l10n_ua_bank_openbanking`, `l10n_ua_bank_payment` встановлюються (тягнуть 13 модулів `l10n_ua_*`, 60 модулів разом),
  33 їхні тести проходять; потрібен пакет `httpx`, якого немає в образі odoo:19. Код без sudo, без сирого SQL, без порожніх except.
  Ціна повторного використання: `l10n_ua_account_base` (2 763 рядки Python і 7 803 XML) плюс `l10n_ua_tax` і `l10n_ua_product_base`
  стають нашою залежністю. Висновок: переписуємо тонкі версії самі (сервіс підпису ~400 рядків, подання в кабінет ~300,
  ПриватБанк ~400, Monobank ~250, ядро виписок ~500), а їхній код беремо як зразок і копіюємо фрагменти з посиланням на LGPL.

Дизайн для нас (три кроки):
1. Сервіс підпису `ua-sign` як контейнер поруч з Odoo: Debian + EUSignCP + Python; методи `sign`, `encrypt`,
   `sign_encrypt`, `decrypt` (для квитанцій); ключ КЕП і пароль - лише в його секретах; журнал усіх операцій.
2. Модуль `l10n_ua_dps_submit` в Odoo: кнопка «Подати в ДПС» на звіті → сервіс підпису → API → зберегти
   квитанцію №1, потім кроном забирати квитанцію №2; статуси на звіті; спершу тестовий контур 9443.
3. Рішення власника: чий КЕП (керівник чи бухгалтер) і де живе файл ключа. Без цього кроки 1-2 працюють лише
   на тестовому ключі.

## Правила Odoo 19, які вже коштували часу

- Групи оголошують через `res.groups.privilege` і `privilege_id`, не `category_id`.
- У пошуковому вигляді `<group>` без `expand` і `string`.
- Фільтр пошуку працює лише на збережених полях.
- Канбан-картка - `<t t-name="card">`.
- Контракт працівника - це `hr.version`; модуля `hr_contract` немає.
