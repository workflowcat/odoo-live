# Карта бекенду: бриф для окремого агента

Задум (Андрій, 2026-09-22): окремий сайт, який показує поточний стан ядра `odoo-live` - усі
моделі, звʼязки, потоки даних, проводки, хто кого викликає - і документує зміни в міру того,
як вони стаються. Не документація руками, а знімок, що будується з коду і з живої бази.
Читачі: Андрій, команда, агенти інших ролей (ui, docs), бухгалтер.

## Як читати ядро

Три входи в Odoo (усі описані в `docs/api/README.md`): `/web/dataset/call_kw` з сеансом,
`/jsonrpc` зовнішній, `execute_kw`. Для карти достатньо читання під користувачем `admin`
на демо-базі. Корисні системні моделі: `ir.model`, `ir.model.fields` (звʼязки many2one /
one2many / many2many, `related`, `compute`), `ir.model.data` (xml id → модуль), `ir.module.module`
(залежності, стан), `ir.ui.menu`, `ir.actions.act_window`, `ir.actions.report`, `account.account`,
`account.journal`, `account.move.line` (проводки), `hr.salary.rule` (правила з python-кодом),
`mis.report` / `mis.report.kpi` (Ф1/Ф2 як вирази над рахунками), `auditlog.rule`.

Статичний розбір коду дає те, чого база не знає: хто кого викликає (`self.env["..."]` у
методах, `super()`, `_inherit`), хуки на завантаження плану (`_post_load_data`), контролери,
що звіт друкує який запис.

## Що має показувати сайт (перша версія)

1. **Карта модулів**: граф залежностей з шарами (нативний Odoo / OCA / наше), розмір, версія,
   тести, чи встановлений у демо. Джерело: маніфести + `layers_check` + `ir.module.module`.
2. **Карта моделей**: для кожної нашої моделі поля, звʼязки, звідки successor/inherit, у яких
   модулях розширена, які методи публічні (з `inventory.json`), які меню/дії ведуть до неї.
3. **Потоки даних** - те, заради чого сайт: ланцюжки, що щось створюють або проводять.
   Мінімум ці: прийняття → наказ → hr.version → листок; місяць (табель → пакет листків →
   compute → проводки → відомість → account.payment.order → платіж 661/333 → виписка → звірка);
   продаж → відвантаження → рахунок → ПН (перша подія) → оплата; закупівля (заявка → RFQ →
   PO → надходження → рахунок → ПДВ-кредит); виробництво (BOM → MO → 231 → 26 → 901 при
   продажу; ЗВВ); інвентаризація 719/947; ОЗ (введення → амортизація); закриття періоду і
   черга змін; консолідація групи. Для кожного кроку: модель, метод, які проводки (Дт/Кт з
   `l10n_ua_payroll_account` map, хуків плану, `mis` виразів), тест, що це покриває.
4. **Проводки**: карта рахунків `ua_psbo`, які модулі пишуть на який рахунок (статично з коду
   + фактично з `account.move.line` демо), рядки правил → Дт/Кт.
5. **Інспектор запису**: за моделлю і id показати запис, звʼязані записи, `_checks()`, слід
   `explain`, auditlog-історію, проводки. Це і є «viewed and inspected».
6. **Зміни**: стрічка з git (коміти `main` за модулем), `docs/api/CHANGELOG.md`, `auditlog.log`
   з демо, нотатки `docs/agents`. Знімок карти версіонується: різниця між двома знімками.

## Технічно

- Окремий репозиторій (`odoo-map` у `/Users/kit/Codius/`), той самий стиль, що `odoo-ui`:
  нічого в ядрі не змінює; якщо бракує методу або даних - request до core через `agent_note.py`.
- Два шари: **екстрактор** (Python, stdlib, читає репо ядра + JSON-RPC демо, пише один
  `snapshot.json` з датою і комітом) і **сайт** (статичний, будується зі знімка; хостинг -
  Cloudflare Pages/Worker як інші сайти; графи - будь-яка легка бібліотека з cdnjs).
- Знімок робиться командою; пізніше - на кожен push у `main` (CI ядра живе в `.github/`,
  володіє сесія UIcore, домовлятися нотаткою).
- Мова сайту українська, без довгих тире, дати YYYY-MM-DD. Стиль - plain reference, без
  продажу і маскотів (це серйозний внутрішній інструмент).
- Не дублювати контракт: посилатися на `docs/api/*`, а не переписувати.

## Що не робити

- Не сканувати `payroll` (стенд 8130) - лише демо 8131 або власна свіжа база.
- Не запускати `docker compose restart` на спільному стенді; свій прогін демо - через
  `DEMO_DB=map DEMO_PORT=8134 ./scripts/demo_server.sh reset` і `ODOO_URL=... PAYROLL_DB=map`.
- Не писати в `addons/`, `docs/api/`, `.github/`.

## Перші кроки для агента

1. Прочитати `README.md`, `CLAUDE.md`, `docs/api/README.md`, `docs/base/demo-space-plan.md`,
   `docs/archive/review-base-2026-09-21.md`.
2. Підняти власну демо-базу (команда вище), переконатися, що `call_kw` під `admin` працює.
3. Екстрактор: модулі + моделі + поля + залежності → перший `snapshot.json`; звірити кількості
   з `inventory.json` (36 модулів наших, 87 моделей, 251 метод, 233 поля станом на 2026-09-22).
4. Сайт: карта модулів і карта моделей зі знімка. Далі потоки (пункт 3 вище), починаючи з
   місяця зарплати - він найкраще покритий тестами і `screens.md`.
5. Зареєструвати роль: `python3 scripts/agent_note.py new decision --from map --to core "..."`.
